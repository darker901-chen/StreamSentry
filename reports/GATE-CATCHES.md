# GATE-CATCHES.md — 多 agent 關卡制度的實際攔截案例

這份文件記錄本專案的自動化關卡(verifier / spec-guardian / scribe,
定義在 .claude/agents/,流程在 ARCHITECTURE.md「Development workflow」)
**實際攔下的問題**。每一件都有對應的報告檔佐證,報告一經提交永不改寫。
記錄目的:(a) 制度有效性的證據;(b) 對外說明工程流程時的實例
(面試/簡報素材 — owner 2026-07-10 指示記錄)。

---

## 案例 1:守門員抓到「保護方向反轉」的邊角(M6,第一輪)

- **背景**:M6 新增通知幾何閘門,需要每 tick 列舉螢幕清單。
- **抓到什麼**:螢幕超過 16 台、或任一台查詢失敗時,清單被截斷;
  截斷的清單會讓「在未列出螢幕上的真通知」判定失敗 → **往「不遮」
  的方向倒**,而且完全沒有記錄。實作者(主 session)自己沒想到這個
  組合。
- **結果**:當場修掉(不完整清單 → 一律視為無法評估),spec-guardian
  以 SendMessage 補審通過。沒有拖到下一個里程碑。
- **佐證**:reports/M6-spec-guardian.md §7。
- **面試講法**:審查者的職責不是「看程式漂不漂亮」,而是逐條對照
  安全準則問「這條路徑失敗時倒向哪邊?」— 人會漏的正是這種
  極端組合。

## 案例 2:verifier 抓到「驗證期間程式被改」(M6)

- **背景**:verifier 在背景做全新建置+測試時,主 session 剛好又
  修了 watcher.cpp(案例 1 的修正)。
- **抓到什麼**:verifier 自己發現 staged diff 的行數變了(642→656),
  判定先前跑的證據已過時 — **主動釘住最終版本重跑整套驗證**,並在
  報告加註「以補遺為準」。
- **為什麼重要**:驗證證據若對應到「舊版程式」,VERIFIED 就是假的。
  這是證據完整性(evidence integrity)的自動防護。
- **佐證**:reports/M6-verifier.md ADDENDUM。

## 案例 3:修憲後,守門員一輪抓出五條違規(M6.5,第一輪 FAIL)

- **背景**:owner 裁決把產品哲學從「fail-closed 黑屏」改成「絕不干擾
  輸出、有把握才遮、失效必須明講」(reports/RULING-2026-07-09-fail-open.md)。
  主 session 改了法規文件和程式,自認完整。
- **抓到什麼(五條)**:
  1. **V1(最有價值)**:螢幕列舉失敗時通知遮罩會**無聲**停擺 —
     沒 log、沒貼片、心跳正常 — 直接違反新法「失效必須告知」。
     實作者翻轉閘門方向時只顧了「不亂遮」,漏了「不能無聲」。
  2. V2:README 開頭仍寫舊承諾「會把畫面變黑」— 對外文件說謊。
  3. V3:兩處 log 字樣仍宣稱會 fail-closed — 誤導除錯的人。
  4. V4:ARCHITECTURE.md 六處自相矛盾(文件跟測試各說各話)。
  5. **V5(最有趣)**:**守門員自己的審核清單還寫著舊憲法**
     (「所有失敗路徑必須落在黑屏」)— 修憲必須連執法者的手冊一起改,
     授權鏈記錄在裁決檔的 Application addendum。
- **佐證**:reports/M6.5-spec-guardian.md(第一輪 FAIL 全文保留)。
- **面試講法**:改「憲法級」規則時,散落在系統各處的舊假設
  (文件、log 字樣、審核配置)不會自己更新;需要一個只認法條的
  審查角色做全面一致性掃描。

## 案例 4:守門員抓到「修 V1 時引入的新 bug」(M6.5,第二輪 FAIL → V6)

- **背景**:V1 的修法是加一個 detection_degraded 旗標讓貼片亮起。
- **抓到什麼**:實作者把旗標併進「unverified」判斷、放在座標映射
  **之前** — 於是降級期間**連完全有把握的黑名單/密碼遮罩也一起
  被丟掉**,違反裁決「有把握的絕不漏遮」。妙的是:同一份 diff 裡
  ARCHITECTURE.md 的表格寫的是正確行為(「block/allowlist + password
  masks still active」)— 守門員的判詞:**「文件符合法律;程式才是
  bug」**。它還指出這條路徑沒有任何自動測試(所以 verifier 全綠),
  建議補回歸測試。
- **結果**:結構性修法 — 把整個「每幀決策」抽成純 C 模組
  frame-decide(不依賴 OBS),V6 情境成為常駐單元測試
  (tests/frame-decide-tests.c),連同理由優先序、過期心跳丟棄遮罩等
  規則一起鎖住。第四個 ctest 套件由此誕生。
- **佐證**:reports/M6.5-spec-guardian.md(re-audit 段)、
  tests/frame-decide-tests.c。
- **面試講法**:最危險的 bug 往往是「修 A 時引入的 B」;而「審查者
  發現 → 不是只修那一行,而是把該類錯誤變成不可能(純函式+回歸
  測試)」是成熟工程的分水嶺。另一個亮點:當文件與程式衝突時,
  用「哪個符合上位規則」裁決,而不是誰後寫誰贏。

## 案例 5:守門員的「QUESTION 機制」逼出一致性決策(M6.5)

- **背景**:新法「拿不準就不遮」與 v0.1 規格的「cloak 狀態查不到就
  照報(寧可多遮)」互相矛盾,散落在舊規格的角落。
- **抓到什麼**:守門員不擅自裁決,而是列為 QUESTION 上報 — 由
  owner 授權的原則(mask only on confidence)統一解決:查不到
  cloak → 視為隱藏 → 不遮,並在舊規格行加註廢止。
- **佐證**:reports/M6.5-spec-guardian.md §8、RULING 檔 addendum #3。
- **面試講法**:審查系統要能分辨「違規(我判)」與「規則衝突
  (人判)」— 越權裁決和漏報一樣危險。

## 制度小結(給第一次看的人)

- 每個里程碑:實作 → **verifier**(從零建置+全測試,只報告不修)→
  **spec-guardian**(逐條對照 CLAUDE.md/SPEC.md 審 diff,FAIL 就擋)→
  **scribe**(只記錄有報告背書的事實)→ commit。
- 三個審查角色**不能改程式**;實作者**不能改報告**。攔截紀錄
  (含 FAIL 全文)永久保留,這份文件只做索引與解讀。
- 規則變更只能由 owner 裁決,記錄為 reports/RULING-*.md 後,
  對所有後續審核生效 — 包括審查者自己的配置(案例 3 之 V5)。
